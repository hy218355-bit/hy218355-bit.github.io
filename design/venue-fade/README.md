# 会場を切り替えた前の響きを、静かに消す

会場を切り替えている途中で、別の会場・聴く位置へ変えると、古い出口にフェードインの予約が残っていた。変更前の実際の音声書き出しでは、0.12秒で約30％だった古い出口の音量が100％まで上がってから消えた（`baseline.json`）。音源をデコードして響きを差し替える経路でも同じ予約処理を使っていた。

`venues.js`の`fadeVenueOut`で未来の予約を取り消し、切り替え時の音量を開始点にして消す。フェード終了後にも明示的な開始点を置き、次の減衰が前の終了時刻から始まらないようにする。`cancelAndHoldAtTime`がない環境では`cancelScheduledValues`を使い、開始点をランプで置いて直前の変化を途切れさせない。

会場と聴く位置、IR、EQ、直接音と響きの比、コンプレッサー、全体の音量は変えていない。0.4秒の切り替えと、デコード後の差し替えの0.3秒も従来どおり。楽譜・成長・採点・セーブ形式・画面の文言は変えていない。新しい素材・フォント・ダウンロード・演出はない。

## 音の測定

`index.html`と`probe.js`は診断専用。実際の`OfflineAudioContext`で48kHzの定数信号を書き出し、製品の音量パラメーターを測る。スピーカーから音は鳴らさない。

- 変更前と修正後を同じ0.4秒・0.12秒で比較。修正後は約30％から0へ減り、再上昇なし。
- 0.3秒と0.4秒、途中2地点とフェード終了後、標準APIと互換処理の12条件。すべて再上昇なし、終了点0。開始点の差は最大約0.0000521で、元のフェードの通常の1サンプル分。
- 製品の`VenueChain`でも、体育館→市民会館→同じ会場の強制差し替え（0.3秒）→客席後方を連続実行。各出口を別チャンネルへ書き出し、古い音が戻らず0になり、最後の出口が1になることを確認。強制差し替えは実際のデコード完了時と同じ`set(..., true)`の経路を使う。
- `pcm-check.json`にサンプル列・切り替え前後の値・条件・結果を保存。`screenshots/pcm.png`はその値を描いた375pxの比較図。
