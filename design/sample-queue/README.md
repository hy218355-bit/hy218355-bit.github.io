# 音源の初回読み込みの負荷を抑える

前回の画面確認で、通常の読み込み時に一部の音源が`Failed to fetch`になり、再試行で揃うことがあった。通信失敗の根本原因は未特定。今回、41個・40,108,511バイトのMP3を一斉に読み込み始めていることを確認した。

`samples.js`の取得・音の展開・頭出しの処理を、一度に4個までの待ち行列にした。取得が終わっただけでは次を始めず、展開とバッファへの登録まで待つ。読めないものがあっても残りを最後まで読み、すべて終わってから再試行を受け付ける。再試行では目録と成功した録音を保ち、足りない分だけ読む。

読み込み済みの41個のバッファは引き続き再生のために保持する。抑えたのは、同時に取得・展開している途中の処理数。最終的に保持する録音の数を減らしたものではない。

音源のファイル、頭出し・発音の遅れ・調律・音量・サンプル選び・再生の処理、ゲームの採点と成長、セーブ形式は変更していない。画面の文章も追加していない。

## 確認

- `check_sample_queue.js`：41個の取得と展開を別々に待たせ、どちらも4個まで。展開が終わるまで次の録音を始めない。先頭のHTTPエラー・展開エラーがあっても後続40個を読み、再試行で成功分のバッファと調律情報を保つ。進捗は完了数に対応し、進行中の呼び出しは同じPromiseを使う。
- この回帰確認を修正前のコードへ適用すると、同時処理が41個になり失敗。`before-regression.json`に記録。既存の音源再試行の確認も成功し、HTTP・目録・音の展開・status 0のアプリ内URL・失敗の繰り返し・本番中の制限も確認。
- 実ブラウザの通常読み込みを3回行い、毎回41個が揃い、取得の同時開始は4個以内。`SampleVoice`で合奏し、部の状態が変わらず、画面のエラーなし。375pxのライト・ダークで横はみ出しなし。
- 意図的にフルートを一度だけ503にした確認ページでも、残り40個まで読み終え、再試行はフルートだけ。40個の同じバッファを保持し、再試行だけでは自動再生しない。その後の合奏は`SampleVoice`。
- `before.json`・`browser-check.json`に記録。計測用ページは実際のセーブや設定を書き換えない。

ブラウザ側で計った取得の開始数は変更前41、変更後4。HTTPの実接続数や端末の使用メモリ量の計測ではない。このMacでの準備完了は、変更前の1回が約1.1秒、変更後3回が約1.5〜1.8秒。負荷の集中を抑える変更で、速度の向上は主張しない。以前の通信失敗が完全になくなったかは、今回の3回だけでは断定できない。

後続の[起動調査](../boot-audit/README.md)で、音源に限らずスクリプトの取得もローカル配信の接続受付で失敗することを再現し、確認サーバーを改善した。ここで記録した4個の処理上限は、引き続き取得・展開の負荷を抑えるために使う。

画像は375×812のPNG。字形チェックは既存の不足記号5字のみ。新しいファイルのダウンロードはない。
