# ローカル配信の読み込み抜けを再現して改善

ゲームの起動時に`FX`・`SEASON_OF`が見つからないことがあった。前回のエラーと同じ時刻の配信ログでは、32本中`fx.js`だけリクエストが残っていなかった。`original-load.json`に一覧を保存。

ゲームのスクリプトより前から記録するページで12回起動し、1回、`flowers.js`が取得できていない状態を再現した。失敗イベントが出て、受信バイト数0・応答状態0。その回は31本しか読み込めていなかった。ゲームのコードを実行する前の取得で起きている。`before.json`に記録。

## サーバーの改善

`design/serve.py`を追加し、8005番のサーバーを切り替えた。

- 作業フォルダのルートを`127.0.0.1`だけへ配信する。
- 接続待ちを128へ広げ、同時取得の入り口で接続が切れないようにする。
- HTTP/1.1で接続を使い回し、ファイルごとの接続の作り直しを減らす。アイドルの接続は30秒で閉じる。
- `Cache-Control: no-store`を保ち、編集前のファイルをキャッシュから出さない。

起動は作業フォルダのルートで`python3 design/serve.py`。ゲームは`http://127.0.0.1:8005/tsukurikata/`、デザインは`/design/`。比較用に起動した8006番と、制御比較用の一時サーバーは停止済み。8005番はこのスクリプトで稼働中。

## 比較

| 確認 | 以前 | 改善後 |
| --- | --- | --- |
| ブラウザでの起動 | 12回中1回でファイル取得漏れ | 比較用24回＋8005番12回、すべて32本取得 |
| 32ファイルを同時取得×3回 | 96件中49件失敗 | 比較用・8005番とも96件すべて内容一致 |
| HTTP/1.0のまま接続待ちだけ比較 | 待ち5で96件中50件失敗 | 待ち128で96件すべて内容一致 |

以前の同時取得の失敗は45件が`ConnectionResetError`、4件が接続エラー。HTTPの方式を同じにした制御比較でも、小さい接続待ちで同じ接続切断を再現し、待ちを広げると取得できた。実際のサーバーではHTTP/1.1での続け読みと、内容のSHA-256の一致も確認している。

32件の同時接続は負荷試験であり、ブラウザの実接続数と同じだとは扱わない。ブラウザでは別に起動を繰り返して確認した。回数の範囲での結果は`summary.json`、個別の応答と内容の比較は`delivery-*.json`・`capacity-*.json`。

## 診断の置き場所

- `probe.js`：ゲームの前からスクリプトの成功・失敗・実行エラーを記録。`DOMContentLoaded`の後に`bootResult`へ結果を出す。未定義の値を補って起動を続ける処理は入れない。
- `fixture.js`：診断専用で保存・読み込みを止め、大きな音源も取得しない。ゲームの計算や製品の起動方法には入れない。
- `build_probe.py`：現在の製品と同じ32本・同じ順の`probe.html`を作る。
- `check_delivery.py`：指定したlocalhostのポートへ32本を同時取得し、実ファイルとの内容一致を記録する。比較用なので失敗もJSONへ記録して終了する。終了値だけで成功とは判定しない。
- `../implementation/build_qa.py`：通常の画面確認ページも製品から生成する。初期のエラーも`qaResult.boot`に残す。製品32本＋確認用1本の33本が揃ったことを確認済み。

画面確認ページで、375pxの4タブ・ライトとダーク・実際の音源41個を読み込んだ合奏も確認。`SampleVoice`で再生し、セーブの状態は変わらず、実行エラーもない。`game-check.json`・`integrated-check.json`と画像に記録。

今回の変更はローカル配信と確認の道具。`tsukurikata/`とiOSアプリの差分はなく、アプリの再ビルドは行っていない。

## 制御比較の再現

`PreviewHandler`のHTTPを1.0へそろえ、`PreviewServer`の接続待ちだけ5と128にした一時サーバーへ、同じ`check_delivery.py`を実行した。どちらも作業フォルダを配信し、テスト後に停止している。元のサーバーの待ち数を実行中のプロセスから直接読んだものではなく、標準の5で症状を再現した比較である。
